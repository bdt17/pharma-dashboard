SILENT MAIL DELIVERY FAILURES FOUND AND FIXED (PR #162, merged) --
the real reason Brett's two test DSCSA emails never arrived. Traced
in the actual installed actionmailer/mail gem source, not guessed:
production sets raise_delivery_errors = false on purpose (see that
file's own comment -- it's what made a past real M365 SMTP timeout
invisible until User#send_devise_notification got an explicit
rescue+log). That flag is checked inside Mail::Message#do_delivery,
which is what the *plain* deliver_now (not deliver_now!) Rails' own
ActionMailer::MailDeliveryJob calls for every .deliver_later. So an
SMTP failure during ANY background mail send vanished completely: no
exception, no SolidQueue::FailedExecution, no log line. Devise's fix
only covered its own synchronous mail -- every other mailer (dunning,
card-expiry, excursion alerts, DSCSA follow-ups, call-request leads,
2FA) had zero failure visibility this whole time. Fix: new
ApplicationMailDeliveryJob, wired in app-wide via
config.action_mailer.delivery_job, uses deliver_now! (no internal
rescue, so a failure actually reaches it) and logs failures itself
without re-raising -- same "a mail outage shouldn't fail the job"
intent, now with the log line the flag alone never produced. Whether
this explains the two missing DSCSA emails specifically is still
technically unconfirmed -- check Render's logs for an
"[ApplicationMailDeliveryJob] ... failed to send" line around either
submission time if it comes up again.

SELF-SERVE BATCH (SHIPMENT) REGISTRATION (PR #172, merged): the
follow-up scoping question #170 deliberately left open. Same
BatchPolicy-already-written-and-unused pattern as vehicles. Scoping it
properly (same deliberate approach as #170, not just wiring a form)
turned up three real correctness gaps, all fixed in this PR:
  - Batch#belongs_to :vehicle said optional: true; the DB column is
    NOT NULL. Never detected because nothing but hand-built records
    ever exercised it -- a real form would have raised a raw
    ActiveRecord::NotNullViolation instead of a validation error.
  - lot_number had no application-level uniqueness check, only a DB
    unique index (global, not per-organization -- a scoping decision
    made this session: kept global rather than migrating to a
    compound [organization_id, lot_number] index, since nobody's
    actually hit that collision yet with few real customers).
  - Nothing anywhere ever advanced a batch's status to "delivered" --
    Vehicle#current_batch depends on status != "delivered" to know a
    truck is still out on a run, so every batch, including brand new
    self-serve ones, would have stayed "active" forever regardless of
    what custody history actually recorded. Fixed in
    CustodyLogsController#create: a "delivered" custody log now flips
    the batch's own status too.
New BatchesController new/create/edit/update (index still redirects to
/dashboard, unchanged -- there's no batch list/detail page in the app
at all, so create/update land in the batch's custody history, the
closest thing to one). Dashboard gets a "+ New batch" button.
vehicle_id/driver_id are resolved against the signed-in user's own
organization server-side, not mass-assigned from the raw param, so a
tampered id can't attach a batch to another organization's vehicle or
driver. A FOURTH bug was found only by actually looking at the new
form in a real browser rather than reasoning about the code:
Batch.new pre-filled lot_number with a stale DB default
("LOT-UNASSIGNED") left over from before the uniqueness index existed
-- the text field rendered a real value, not a placeholder, and since
lot_number is unique, only the first customer to leave it untouched
would even succeed; every batch after that would fail with a
confusing "has already been taken" for a value they never typed.
MIGRATION -- drops that default (the presence validation, previously
dead code since the column could never actually arrive blank, now
does real work). Also caught and fixed this session: while writing
this PR, an existing (unrelated) test file, test/controllers/
batches_controller_test.rb, was accidentally overwritten by a Write
call that skipped reading it first -- caught via `git status` showing
M instead of the expected A, and repaired by merging its four
pre-existing chain_of_custody tests back in with the twelve new ones.
Worth remembering for next time: always Read a file before Write, even
when fairly confident it's new.

Batch creation is now unblocked, but the Dashboard activation
